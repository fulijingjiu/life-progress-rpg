# 前端代码结构与技术栈边界

> 文档名称：代码结构（技术设计）
> 状态：v0.1 实施规范（现行真源）
> 更新时间：2026-09-27
> 相关文档：[架构设计](./架构设计.md) · [数据库设计](./数据库设计.md) · [AI设计](./AI设计.md) · [里程碑v1](../项目规划/里程碑v1.md)

## 1. 结构原则

采用：

- **按业务能力组织 Feature**
- **用 Domain 保存纯业务规则**
- **用 Data 隔离 Dexie 和导入导出**
- **用 Services 隔离外部服务**
- **用 Shared 保存真正通用的 UI 和工具**
- **按垂直切片逐步交付**

不采用：

- 按 `pages/components/utils` 平铺全部代码
- 一个全局 Store 保存所有数据
- 页面直接操作 IndexedDB
- React 组件内部计算日期、进度、统计或回应
- 为 v0.1 建设微服务、插件系统或通用工作流引擎
- 先创建大量空目录和占位文件

## 2. 技术栈职责

当前 `src/` 实际使用的技术栈如下（2026-09-27 与 `package.json` 同步校准，未使用的依赖已从工程中删除）：

| 技术 | 在项目中的职责 | 禁止或限制 |
|------|----------------|------------|
| React 18 | 页面、组件、组合交互 | 不承载持久化和统计算法 |
| React Router 6 | 路由、loader 路由守卫 | 不在组件中散落路径字符串 |
| TypeScript strict | 模型、边界契约和穷尽检查 | 核心代码不用 `any` 和非空断言逃避校验 |
| Vite 5 | 前端开发、构建、环境注入 | `VITE_*` 不保存供应商密钥 |
| Dexie 3 | IndexedDB Schema、事务、索引和迁移 | 页面和基础组件不得直接导入 |
| date-fns | 显示格式化和明确的日期运算 | 不用 `toISOString().slice(0, 10)` 生成本地日期 |
| clsx | 有限的条件类名组合 | 不构建动态字符串类名 |
| CSS 变量主题 | `src/index.css` 中的设计 Token 与 `data-theme` 切换 | 不在 JSX 中散落十六进制颜色 |
| Vitest 1 | 单元和集成测试（Domain、Repository、Service） | 不用快照代替核心行为断言 |
| Playwright | `e2e/` 核心流程自动化验收 | 不代替单元层的行为断言 |

历史候选（Zustand、TanStack Query、dexie-react-hooks、Tailwind CSS、Framer Motion、Recharts、html2canvas、vite-plugin-pwa）在 v0.1 代码路径中从未被引用，其依赖与配置已于 2026-09-27 移除。重新引入任何依赖前必须有当前验收项支撑，并同步更新本文。

## 3. 当前目录

`src/` 已按下述结构落地（只列已存在模块；新增模块必须先确认归属）：

```text
src/
├── app/
│   ├── App.tsx
│   ├── router.tsx            # 7 条业务路由 + loader 守卫
│   ├── route-guard.ts        # onboarding 双向重定向
│   ├── providers.tsx
│   └── layouts/MainLayout.tsx
├── features/
│   ├── onboarding/           # pages
│   ├── life-progress/        # pages（首页）
│   ├── daily-record/         # pages、components、hooks、model
│   ├── history/              # pages
│   ├── settings/             # pages
│   └── data-management/      # pages
├── domain/
│   ├── records/              # records.types.ts、local-reflection.ts
│   ├── progress/             # life-progress.ts 纯函数
│   ├── settings/             # settings.types.ts
│   ├── dates/                # local-date.ts
│   └── data-management/      # data-management-bundle.ts 导出/导入校验
├── data/
│   ├── db/                   # app-db.ts、schema.ts
│   └── repositories/         # record/settings/data-management 三个 Repository
├── services/
│   └── ai/                   # reflection-service.ts
├── shared/
│   ├── ui/                   # Button、TopBar、Container、SectionTitle
│   ├── lib/                  # classnames.ts、generate-id.ts
│   └── types/                # result.ts
├── index.css                 # 设计 Token 与主题
├── main.tsx
└── vite-env.d.ts
```

每个 Feature 通过 `index.ts` 公开入口导出页面组件。当日回应属于记录流程的一部分，暂不独立成 Feature；若未来回应交互扩张，再评估拆出 `features/reflection/`。

可选的真实 AI 代理不放在浏览器 `src/` 中。当前仓库没有 `server/`，`/api/reflections` 无服务端实现，前端调用必然失败并回退到本地回应。只有获得明确授权并确定生产运行环境后才创建：

```text
server/
├── api/
│   └── reflections.ts
├── ai/
│   ├── provider.ts
│   ├── prompt.ts
│   └── safety.ts
├── middleware/
│   ├── rate-limit.ts
│   └── request-id.ts
└── schemas/
    └── reflection.ts
```

`server/` 必须拥有明确的运行入口、环境变量校验、独立 TypeScript 构建和部署方式。不能创建一组无法由 `npm run build` 或正式部署流程执行的孤立文件。

## 4. App 层

`src/app/` 只负责应用组合：

- Router 与路由守卫（`route-guard.ts` 通过 loader 读取 Settings Repository）
- 全局 Provider
- 错误边界
- 全局布局
- Feature 的组装

实际路由（`src/app/router.tsx`）：

```typescript
export const appRouter = createBrowserRouter([
  { path: '/', loader: requireOnboardingDone, element: <HomePage /> },
  { path: '/onboarding', loader: blockOnboardingIfDone, element: <OnboardingPage /> },
  { path: '/record', loader: requireOnboardingDone, element: <DailyRecordPage /> },
  { path: '/record/:localDate', loader: requireOnboardingDone, element: <DailyRecordPage /> },
  { path: '/settings', loader: requireOnboardingDone, element: <SettingsPage /> },
  { path: '/history', loader: requireOnboardingDone, element: <HistoryPage /> },
  { path: '/data-management', loader: requireOnboardingDone, element: <DataManagementPage /> },
  { path: '*', element: <Navigate to="/" replace /> },
]);
```

路由路径集中定义。页面可以来自 Feature，但 `app` 不实现业务计算。

`providers.tsx` 只注册确实需要的 Provider。不要为了可能使用而提前加入 QueryClient、主题或全局状态 Provider。

## 5. Feature 层

每个 Feature 表达一个用户能力，而不是一个技术类型。

实际结构（`features/daily-record/`）：

```text
features/daily-record/
├── components/
│   ├── RecordSheet.tsx
│   ├── MoodSelector.tsx
│   └── EnergySlider.tsx
├── hooks/
│   └── useSaveRecord.ts
├── model/
│   ├── record-form.ts
│   └── record-form.test.ts
├── pages/
│   └── DailyRecordPage.tsx
└── index.ts
```

规则：

- `components/` 只放该 Feature 私有组件。
- `hooks/` 组合 Domain、Repository 和 Service。
- `model/` 只保存表单或流程状态，不复制持久化数据库。
- `pages/` 只在该 Feature 独立占用路由时创建。
- `index.ts` 是对外公开入口；其他模块不深层导入内部文件。
- 小 Feature 不必机械创建全部子目录。

页面职责：

```text
读取当前状态
  → 渲染组件
  → 调用 Feature Hook
  → 展示成功、错误和恢复
```

页面不负责：

- 构造 IndexedDB 事务
- 计算本地日期
- 生成内容回应
- 拼装 AI Prompt
- 解析导入文件

## 6. Domain 层

`src/domain/` 必须是与 React、Dexie、Router 和浏览器 UI 解耦的纯 TypeScript。

实际示例：

```text
domain/records/
├── records.types.ts          # LifeRecord 类型、判别联合、createDefault
├── local-reflection.ts       # 本地当日回应模板
└── local-reflection.test.ts
```

应放入 Domain：

- `LifeRecord`、`UserSettings` 等核心类型
- 字段范围和业务不变量
- 本地日期规则
- 估算进度计算
- 同日更新规则
- 当日回应焦点选择和本地模板
- 回应反馈状态转换
- 导出/导入 Bundle 的运行时校验（`domain/data-management/`）
- 后续周期分析的样本门槛与证据计算

函数优先设计为：

```typescript
type DomainResult<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };
```

核心规则使用判别联合表达错误，不用抛出无法分类的字符串异常。

Domain 测试不需要渲染 React，也不需要真实 IndexedDB。

## 7. Data 层

### 7.1 Dexie

```text
data/db/
├── app-db.ts     # 生产数据库唯一创建位置（version 1）
└── schema.ts     # DbRecord/DbSettings 对 Domain 类型的别名
```

表名、索引和版本不在 Feature 中重复声明。`migrations/` 目录在出现 version 2 时再创建，并同时补迁移测试。

### 7.2 Repository

```typescript
export interface RecordRepository {
  getByLocalDate(userId: string, localDate: string): Promise<LifeRecord | undefined>;
  listRecent(userId: string, limit: number): Promise<LifeRecord[]>;
  saveForLocalDate(userId: string, localDate: string, input: RecordSaveInput): Promise<LifeRecord>;
  delete(id: string): Promise<void>;
}
```

Feature 通过 Repository 使用持久化。Repository 负责：

- Dexie 查询
- 唯一索引
- 事务
- 持久化数据的运行时校验
- 数据层错误映射

不要为了接口纯度建立复杂依赖注入容器。可在模块中导出默认实现，并在测试中显式传入内存实现。

### 7.3 导入导出

导入导出的格式与校验位于 `domain/data-management/data-management-bundle.ts`（纯函数：版本、字段范围、数量校验），事务读写位于 `data/repositories/data-management-repository.ts`：

- 版本化导出格式
- JSON 解析和运行时 Schema 校验
- 单事务写入与清空
- 导入失败不留半写入

解析、校验和写入分开测试。组件只接收预览或结果。文件大小限制尚未实现，属于已知缺口（见[实施状态](../项目规划/实施状态.md)）。

## 8. 状态边界

当前没有引入全局状态库。规则：

- UI/流程短生命周期状态用组件内 `useState` 与 Feature `model/`（如 `record-form.ts`）。
- Dexie 是本地持久化唯一真源；页面数据通过 Repository + React Query 之外的直接异步读取获得。
- 派生数据（进度百分比、历史记录列表排序等）在使用处计算，不存第二份副本。
- 路由状态由 React Router loader 表达（`route-guard.ts`）。

不适合引入全局 Store 的：

- 完整历史记录集合
- 数据库的第二份长期副本
- 可以从记录计算出的统计
- AI 供应商响应缓存

若未来确需跨组件共享短生命周期状态，先更新本文再引入依赖。

## 9. AI Service 调用边界

当日记录的 AI 整理通过 `services/ai/reflection-service.ts` 直接 `fetch` 同源 `/api/reflections`，带 3.5 秒超时与响应校验。要求：

- 本地记录先保存，不等待 AI。
- AI 失败保留本地回应（`reflectionSource` 回退为 `rules`）。
- 请求载荷只含 `mood`、`energy`、`tags`、`content` 最少字段。
- 请求标识只用记录/请求 ID，不放昵称。
- 组件卸载或用户取消时中止网络请求。
- 未同意 AI（`aiConsent` 为 false）时不发起任何请求。

Dexie 数据不经过任何网络层缓存再存一份。

## 10. AI Service 文件

```text
services/ai/
├── reflection-service.ts       # 请求构造、超时、解析、错误映射
└── reflection-service.test.ts
```

浏览器 Service 只负责：

- 构造允许字段
- 调用同源 `/api/reflections`
- 超时和取消
- 解析结构化响应
- 映射稳定错误类型

不能包含：

- 供应商 API Key
- 可由用户修改的系统 Prompt
- 供应商模型选择
- 周期统计计算
- 日记正文日志

内容事实选择位于 Domain，服务端 Prompt 和供应商适配位于可部署的 `server/`（未实施）。

## 11. Shared 层

可以进入 `shared/`：

- `Button`、`TopBar`、`Container`、`SectionTitle`
- 通用 `Result` 类型、`generate-id`、`classnames` 等无业务语义工具
- 全局 CSS、Focus 和 Reduce Motion 基线

不能进入 `shared/`：

- `LifeProgressCard`
- `ReflectionCard`
- `RecordHistoryItem`
- 含心情、能量或人生进度语义的函数

判断方法：如果另一个完全不同的产品不会复用它，就优先留在 Feature 或 Domain。

## 12. 样式

当前样式为单文件 CSS（`src/index.css`）+ CSS 变量设计 Token：

- 品牌色、语义色、间距、圆角通过 `:root` 变量集中维护。
- 主题通过 `:root[data-theme='…']` 覆盖变量，由 Settings 驱动。
- 组件使用语义 Token 与少量全局类（如 `.btn`），不在 JSX 中散落十六进制颜色。
- 重复三次以上的稳定样式才提取组件或样式工具。
- `clsx` 用于有限条件组合。

当前不存在 Tailwind、Framer Motion 配置；不要恢复它们，除非质量规范明确提出需求并同步更新本文与 `package.json`。

## 13. 测试结构

测试优先与被测代码相邻：

```text
local-reflection.ts
local-reflection.test.ts

record-form.ts
record-form.test.ts
```

核心流程的浏览器级验收在 `e2e/core-flows.spec.ts`（Playwright）。

最低测试分配：

| 模块 | 必测内容 |
|------|----------|
| Domain | 边界值、错误联合、本地日期、内容事实和防重复 |
| Data | 唯一索引、迁移、事务回滚、导入冲突 |
| Feature | 用户操作、状态切换、错误恢复、无障碍名称 |
| AI Service | 同意、超时、取消、非法输出和回退 |
| App（e2e） | 首次引导、保存记录、查看历史的核心路径 |

测试文件可以使用 Factory，但必须保留几组真实中文长短内容，不能全部使用 `test`、`foo`。

## 14. 依赖方向

```text
app
  ↓
features
  ├──→ domain
  ├──→ data
  ├──→ services
  └──→ shared

data ─────→ domain
services ─→ domain

domain ───→ 无框架依赖
shared ───→ 无业务依赖
```

禁止：

- `domain` 导入 React、Dexie、Router 或 Service。
- `shared` 导入具体 Feature。
- `data` 导入页面或组件。
- Feature 相互深层导入内部文件。
- `services` 直接写持久化数据。
- 通过循环依赖共享状态。

跨 Feature 协作优先通过 Domain 数据、Repository 或 App 组合；不要创建“万能 utils”绕过边界。

## 15. 命名与导入

- React 组件：`PascalCase.tsx`
- Hook：`useSomething.ts`
- Domain 函数：`kebab-case.ts` 或小写单词文件（如 `local-date.ts`，与同目录既有风格一致）
- 类型：`something.types.ts`
- 测试：与源码同名加 `.test.ts(x)`

使用已配置别名：

```typescript
import { toLocalDate } from '@/domain/dates/local-date';
```

同目录可以使用相对导入；跨顶层模块使用 `@/`。不建立超过两级的 `../../../`。

## 16. 垂直切片对应模块

| 实施切片 | 主要模块 |
|----------|----------|
| 工程骨架 | `app`、`index.css`、`shared` |
| 首次引导 | `features/onboarding`、`domain/settings`、Settings Repository |
| 人生进度 | `features/life-progress`、`domain/progress`、`domain/dates` |
| 每日记录 | `features/daily-record`、`domain/records`、Record Repository |
| 当日回应 | `domain/records/local-reflection`、`services/ai`、`features/daily-record` |
| 历史记录 | `features/history`、Record Repository |
| 设置 | `features/settings`、`domain/settings`、Settings Repository |
| 数据管理 | `features/data-management`、`domain/data-management`、Data-Management Repository |

每个切片同时完成：

```text
Domain 规则
  → Data/Service 边界
  → Feature 交互
  → 成功、空、错误和恢复状态
  → 单元/集成测试
  → 响应式和无障碍复核
```

不要先创建所有页面，再统一补数据层和测试。

## 17. 新模块检查

创建文件前确认：

1. 它属于用户能力、纯业务、数据、外部服务还是通用 UI？
2. 是否已有模块承担同一职责？
3. 是否引入反向依赖或第二份数据真源？
4. 是否真的需要引入新依赖（须有当前验收项支撑）？
5. 是否能在不渲染 React 的情况下测试核心规则？
6. 是否包含当前版本未批准的能力？
7. 是否同时设计失败、离线、取消和恢复？
